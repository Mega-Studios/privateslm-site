Three models in our catalog open a <think> block. Our engine deletes it before the model sees a token.

August 24, 2026 · 11 min read

Liquid AI documents LFM2.5-2.6B as "a pure reasoning model that always thinks before it answers," and its chat template backs that up in the bluntest possible way: line 124 ends every prompt with a literal <think> tag, unconditionally, with no flag to turn it off. Our app ships that model. It reads that exact template out of the GGUF. And then it hands the model a prompt ending in <|im_start|>assistant\n — with no <think> anywhere in it.

That isn't a bug in our code. The llama.cpp C function we call to render chat templates does not render chat templates. It reads yours, compares it against 55 hardcoded C++ emitters, picks whichever one looks closest, and emits that instead. Exactly one of those 55 ever writes a <think> tag, and it belongs to a model family we don't ship.

The function whose own header tells you

The API is llama_chat_apply_template(), and to its credit it does not hide this. From include/llama.h at our pinned release, b10488, line 1206:

/// Apply chat template. Inspired by hf apply_chat_template() on python.
///
/// NOTE: This function does not use a jinja parser. It only support a
/// pre-defined list of template. See more: ...Templates-supported-by-llama_chat_apply_template

And the signature, at line 1214:

LLAMA_API int32_t llama_chat_apply_template(
                          const char * tmpl,
        const struct llama_chat_message * chat,
                              size_t   n_msg,
                                bool   add_ass,
                                char * buf,
                             int32_t   length);

Six parameters. There is no seventh for template variables, which means there is no way — none, at any call site, in any app — to pass enable_thinking, reasoning_effort, or any other keyword argument the model's real template branches on. The information simply has nowhere to go.

What our app actually calls

Our engine wrapper, Sources/LlamaEngine.swift, pulls the template string out of the model file and passes it straight in. Line 231:

rendered = Self.render(cMessages, tmpl: llama_model_chat_template(model, nil))

and render, at line 241, calls the function above. So we are doing the ordinary, documented thing that a native app linking libllama does. We fetch the model's own template and ask llama.cpp to apply it. The gap opens inside that second step.

The 55-way guess

Inside src/llama-chat.cpp, the template string is first looked up as a name — "chatml", "gemma", "deepseek3" and 51 others (54 are addressable by name; one more, dots1, is reachable only by content detection, for 55 emitters in total). We don't pass a name; we pass several kilobytes of Jinja source, so that lookup misses and the code falls through to a chain of substring tests. The very first one, at line 101, decides the outcome for most modern models:

if (tmpl_contains("<|im_start|>")) {
    return tmpl_contains("<|im_sep|>")
        ? LLM_CHAT_TEMPLATE_PHI_4
        : tmpl_contains("<end_of_utterance>")
            ? LLM_CHAT_TEMPLATE_SMOLVLM
            : LLM_CHAT_TEMPLATE_CHATML;
}

That branch is a one-way door. Any template mentioning <|im_start|> resolves to ChatML (or Phi-4, or SmolVLM) right there, and none of the remaining rules ever run. LFM2.5-2.6B's template mentions <|im_start|> three times, <|im_sep|> zero times and <end_of_utterance> zero times — we checked the raw file — so it lands on plain ChatML. There is no LFM2 emitter in the list to land on anyway; we grepped every name in that table and every enum member beside it, and LFM2 is in neither, despite lfm2 being a fully supported architecture in the same build.

And here is the ChatML emitter it gets instead, line 250:

if (tmpl == LLM_CHAT_TEMPLATE_CHATML) {
    for (auto message : chat) {
        ss << "<|im_start|>" << message->role << "\n"
           << message->content << "<|im_end|>\n";
    }
    if (add_ass) {
        ss << "<|im_start|>assistant\n";
    }
}

Nine lines, no <think>, no conditionals, no knowledge that the model it's formatting for was trained to expect one. Searching the whole file for a <think> emission returns a single hit, at line 741, guarded by LLM_CHAT_TEMPLATE_BAILING_THINK — Ant Group's Ling family. Every other reasoning model in the world, routed through this API, gets its thinking prefill silently dropped.

What it costs us, model by model

We ran the same check across our eight Generalist catalog entries against the templates their vendors publish. Every one of the five readable templates below contains <|im_start|>, so every one resolves through that first branch.

Gemma 2 2B and Llama 3.2 3B are omitted because their template files sit behind a gated licence our fetch can't read — not because they were checked and cleared. Phi-4 Mini's template contains no <|im_start|> and takes a different path we haven't traced.

G9v3-3B deserves the asterisk. Its template only writes a think marker when enable_thinking is explicitly set either way; omit it and the template writes nothing. Since our API physically cannot pass that variable, the "correct" Jinja output and our ChatML approximation happen to agree. We get the right prompt for the wrong reason, and if AI9Stars ever changes that default we'd never notice.

The other template engine, in the same repository

Here's the part that turns this from a limitation into a choice. llama.cpp does ship a real Jinja engine. It lives in common/jinja, it's used by llama-server and llama-cli through common/chat.cpp, and it handles exactly the things the C API cannot:

bool common_chat_templates_support_enable_thinking(...)   // chat.cpp:357
const std::map<std::string, std::string> & chat_template_kwargs  // chat.cpp:685
{"enable_thinking", inputs.enable_thinking},              // chat.cpp:946

There is even a --chat-template-kwargs command-line flag, and common/arg.cpp carries a deprecation warning telling you to use --reasoning-budget instead — a whole feature surface built around the variable our path can't carry. The repo ships models/templates/LFM2.5-Instruct.jinja as a test fixture, so the project is explicitly testing LFM2.5's real template through the Jinja path while the C path has no LFM2 entry at all.

So one binary contains two chat-template systems: a correct one in libcommon, and a 55-entry lookalike in libllama. Which one you get depends entirely on which library you linked, and nothing at runtime tells you which you're using or which of the 55 guesses your model landed on. That's the real finding. It isn't that llama.cpp is wrong — it's that the fast, obvious integration path for a native app is the lossy one, and it fails silently by design.

The failure mode we have to own separately

Dropping the prefill is one half. The other half is what happens if a model emits <think> on its own anyway — which a reasoning model trained to do so will often do, prefill or not.

Our reply-length default is 512 tokens (LlamaSettings.swift, line 12), and that cap covers the whole generation, thinking included (LlamaEngine.swift, line 55). Our UI parser, ChatView.parseThink at line 211, splits a reply on <think> … </think>. If the closing tag never arrives because the cap cut generation off mid-thought, it returns the thinking text and an empty answer string — and the view at line 188 renders a collapsed "Thinking…" disclosure with nothing beside it. No answer, no error, no hint that a length limit is responsible. The user gets a permanently thoughtful, permanently silent assistant.

This is not hypothetical elsewhere either. Ollama has an open issue, #17561 (mann1x, 4 August 2026), proposing exactly the fix this needs — a separate thinking budget. It restates the problem from a linked issue, #16583: "thinking mode consumes the entire num_predict token budget with internal reasoning, leaving no tokens for the actual response." In the reporter's own test, think: true returned 7,208 characters of reasoning and zero characters of content, while capping thinking at 256 tokens returned 614 characters of reasoning plus 6,186 characters of usable answer. Same budget, useful answer, because the reasoning was bounded instead of the reply.

Why this bites hardest on a phone

Reasoning defaults are set by people benchmarking on datacenter hardware. Qwen3.8-27B's model card lists xhigh as its default reasoning_effort — "for complex tasks demanding thorough analysis" — and states the model "operate[s] in thinking mode by default." Simon Willison measured what that costs locally: 22,276 reasoning tokens to produce 3,223 tokens of output on a draw-me-an-SVG prompt, 21 minutes end to end on a 128 GB M5 Max at LM Studio's 15–30 tokens a second. The same prompt with reasoning off finished in 137 seconds. He calls the default "absolutely not a good way to run the model, especially on consumer hardware."

Now scale the hardware down to what our users actually hold. The sustained-load study behind our thermal-cliff post measured Qwen 2.5 1.5B at 4-bit on an iPhone 16 Pro peaking at 40.49 tok/s and settling to a Hot-state 23.67 ± 0.28 tok/s, and a Galaxy S24 Ultra averaging 10.83 tok/s (CV 6.9%). At the iPhone's sustained rate, every 1,000 tokens of thinking is 42 seconds of staring at a blank bubble before the answer starts. On the Galaxy, 92 seconds. That's the arithmetic, and it's ours — we do not have a measured thinking-token distribution for the specific 3B models in our catalog on phone hardware, and we're not going to borrow Qwen3.8-27B's 22,276 and pretend it transfers to a 2.6B model.

What we can't claim

Three honest limits on all of the above.

We have verified the prompt our engine constructs by reading the code paths end to end. We have not instrumented a device to dump the final prompt string, and we have not measured whether LFM2.5-2.6B and Nanbeige4.2-3B recover on their own — emitting <think> unprompted because that's what they were trained to do — or whether the missing prefill degrades their answers measurably. Both are plausible. Neither is established, and "the vendor's specified prompt is not what we send" is a defect regardless of how gracefully the model copes.

Second, two of our eight Generalists sit behind gated licences our automated fetch can't read, so that table has holes we've marked rather than filled.

Third, this is a template-layer problem, not the architecture-support problem we wrote about in July. Those models load and run fine. This is the layer above: the model loads, the architecture is supported, generation works, and the prompt is quietly not the one the model was trained on.

What we're doing about it

The fix is to stop calling llama_chat_apply_template and render the model's real template through the Jinja path that already exists in the same source tree — which for a Swift app means linking or bridging libcommon rather than libllama alone, a heavier build than the xcframework we currently fetch. That's a real piece of work, not a one-line patch, and we're not going to announce a ship date we haven't scoped.

The smaller, immediate change is the reply cap. A 512-token default that silently swallows a reasoning model's entire output is indefensible now that we've traced it, and bounding thinking separately from the reply — the thing Ollama's issue asks for — is the correct shape of the fix.

The reason to publish this before either lands is that no user could have discovered it. There is no log line, no warning, no setting, and no observable difference except answers that are slightly worse than the model can produce. If you're building on libllama directly, you have this too, and you can check it in about a minute: grep your model's template for <|im_start|>, and if it's there, you're getting ChatML no matter what else that template says.
