SLM Daily #10: a new model's GGUF is 256 bytes from one already in our catalog

August 14, 2026 · 5 min read

Liquid AI shipped a new vision-language model this week, LFM2.5-VL-3B, and its text-generation weights quantize to 1,684,023,328 bytes at Q4_K_M. LFM2.5-2.6B — the text-only generalist already sitting in our catalog since SLM Daily #8 — quantizes to 1,684,023,584 bytes. That's a 256-byte gap between a brand-new model and one we shipped eight days ago, and it isn't a coincidence: it's the same LFM2.5 language backbone, with a vision encoder bolted on that privateSLM's app has no way to use yet. Zero catalog changes this edition — but there's more happening in the engine and the wider field than that one number suggests.

What actually shipped since our last check

LFM2.5-VL-3B (Liquid AI, Aug 11–12, 2026) — a 3.1B vision-language model extending last year's LFM2-VL line with screen understanding, object grounding, and function calling, 128K context. Official and bartowski GGUF quants exist, Q4_K_M at 1.68 GB comfortably under our 2.5 GB cap. We checked: privateSLM has no image-attachment UI, no mmproj-loading code path, and no roadmap item for one — we confirmed this directly in the app's own source, not just inferred it. Downloading this model today would buy users the exact same text generalist already in the catalog, plus a 0.85 GB mmproj file (f16) that our app can't load and wouldn't know what to do with if it did. Skipped, and it wouldn't strictly dominate the LFM2.5-2.6B entry it would sit next to even if we could use it — same backbone, extra dead weight.

deepgrove Maple-Preview (Aug 4–6, 2026, MIT license) — a genuinely new architecture: a ternary-weight (2-bit-class) reasoning MoE, 20.2B total parameters with only 1.49B active per token, 256 experts with 8 active, dedicated TQ1_0/TQ2_0 GGUF quant types built for it. We verified its smallest published GGUF directly: maple-preview-TQ1_0-head-Q4_K.gguf is 4,984,016,416 bytes — just under 5 GB, exactly 2x our 2.5 GB phone cap. Even at roughly 1.5–2 bits per weight, 20B total parameters (every expert ships in the file, whether or not it's active for a given token) doesn't compress far enough. Genuinely new architecture, correctly excluded on size alone.

Meta Muse Glimmer (30B dense, Apache 2.0, Aug 10–11) — llama.cpp merged support in build b10353 (PR #26841); we confirmed LLM_ARCH_MUSE_GLIMMER is live in the current src/llama-arch.h. A 30B dense model doesn't get near a phone at any quant we'd ship, engine support or not.

IBM Granite-Switch — the underlying model (ibm-granite/granite-switch-4.1-8b-preview, 12 embedded LoRA "personalities" switched per-token by an in-graph router-attention mechanism) released back in May, but working llama.cpp support only landed this week in build b10342, after an earlier approach was scrapped for multi-turn concurrency bugs. We confirmed LLM_ARCH_GRANITE_SWITCH is now in the arch enum. Still an 8B-class checkpoint — outside our size cap regardless of how novel the routing mechanism is.

NVIDIA Nemotron 3.5 Lightning (30B-A3B hybrid Mamba-2/MoE/Attention, Aug 11) — notable mainly because it was pretrained natively in 4-bit NVFP4 across 20T+ tokens rather than trained in bf16 and quantized after the fact. Interesting for what "full precision" means as a baseline going forward; far too large for our catalog either way.

The catalog now

Still 22 models — 8 Generalists at our self-imposed cap, 14 pre-cap specialist entries (medical, legal, finance and similar) we haven't unilaterally pulled. Unchanged since SLM Daily #9. Nothing this edition strictly dominated an existing Generalist slot, so nothing was replaced.
